bfields

The bPlugins settings and meta-box framework. You register options pages and meta boxes with Codestar-style PHP arrays, and bfields draws them as a React interface inside wp-admin. Your field arrays, stored data and csf_* hooks keep working as they are.

InstallationBundle the library in a plugin and boot it. Quick startA working options page in about 30 lines. Fields28 field types, each with its arguments and stored shape. Migrating from CodestarChange one call per screen. The data stays where it is.

What it is

bfields is a JavaScript body on a PHP spine. PHP registers menus and meta boxes, checks capabilities and nonces, sanitizes on save, seeds defaults and bridges hooks. The browser receives each screen as one versioned JSON document (the schema) and renders it with React. When you save, the browser sends back one JSON document of values.

The public API is a drop-in for Codestar Framework's static calls:

// Codestar
\CSF::createOptions( '_my_settings_', $args );
\CSF::createSection( '_my_settings_', $section );

// bfields: same arrays, different class
\BFields\Compat\Codestar::createOptions( '_my_settings_', $args );
\BFields\Compat\Codestar::createSection( '_my_settings_', $section );

The one rule: zero data loss

bfields keeps Codestar's storage contract byte for byte. Each screen is stored as one serialized array under its unique key, with the same field ids and value shapes. Switchers are '1'/'0', media is an 8-key array, dimensions are {width, unit} and groups are lists of rows. There is no migration step. Every reader in every host plugin depends on those exact shapes.

  • Read-modify-write on save. A save overwrites only the ids the current field set declares. Other keys in the row are left as they are, such as Pro settings during a licence lapse or keys an older version wrote. Codestar replaces the whole array and drops them.
  • An absent payload is a no-op, never a delete. If the bundle fails to load, saving cannot blank a user's settings.
  • Untouched values round-trip verbatim. The browser holds values in their stored shape, so a field the user never touched is written back as the same bytes, key order included.

Requirements

  • PHP 7.4 or newer.
  • WordPress 6.5 or newer. On 6.5, bfields provides the react-jsx-runtime script that WordPress only registers from 6.6.
  • The classic editor screen for meta boxes (a post type with show_in_rest off, or the Classic Editor plugin). Meta boxes render inside #poststuff.

What it does not do

bfields covers Codestar's options pages and meta boxes. Keep these Codestar features on Codestar:

  • createCustomizeOptions(), createShortcoder() and createWidget(). The facade has these methods, but they only trigger _doing_it_wrong() and register nothing.
  • Nav menu, taxonomy, profile and comment options. The facade has no createNavMenuOptions(), createTaxonomyOptions(), createProfileOptions() or createCommentOptions(), so calling one is a fatal error.
  • Options storage other than wp_options, meaning Codestar's database values transient, theme_mod and network. Registering one triggers _doing_it_wrong(), and saves are refused.
  • Meta boxes with 'data_type' => 'unserialize' (one meta row per field). The box triggers _doing_it_wrong() and is neither shown nor saved.
  • Some field types. See Unsupported field types. Their values are still preserved.

Getting Started

Installation

bfields is a library, not a plugin. Each host plugin bundles a copy. When several plugins bundle different versions, the newest copy wins and the others share it.

1. Build the package

From a checkout of the bfields repo:

npm install
npm run dist        # builds the bundle, then writes dist/bfields.zip

dist/bfields.zip contains only what a host needs:

bfields/
  php/          the PHP spine (bootstrap, loader, compat layer)
  build/        the compiled JS + CSS bundle, fonts, RTL stylesheet
  languages/    bfields.pot
  README.md
  composer.json

2. Put it in your plugin

Unzip it into your plugin at lib/bfields/ and commit it.

Not in vendor/Host plugins gitignore vendor/, so a fresh clone would not build. Hosts never run composer install for bfields either, because it has its own autoloader.

3. Load the bootstrap

Require the bootstrap from your main plugin file, at load time and outside any hook:

require_once __DIR__ . '/lib/bfields/php/bootstrap.php';

The bootstrap does not define any classes. It records this copy's version and path. On plugins_loaded (priority -1000), the newest recorded copy loads and fires bfields_loaded.

4. Register your screens

Register on init, from inside bfields_loaded:

add_action( 'bfields_loaded', function () {
	add_action( 'init', function () {
		\BFields\Compat\Codestar::createOptions( '_my_settings_', array( /* … */ ) );
		\BFields\Compat\Codestar::createSection( '_my_settings_', array( /* … */ ) );
	}, 1 );
} );
Why this order matters
  • bfields_loaded guarantees the classes exist and come from the winning copy.
  • Registering on init lets your labels use your own text domain.
  • Defaults are seeded on init priority 99, so an options page must be registered before that.

Which copy is loaded?

$GLOBALS['bfields_loaded_from'] holds the path of the loader that won. At equal versions, the copy registered last wins, which depends on plugin load order. To force one copy during development, such as a checkout next to a host's lib/bfields/, define BFIELDS_FORCE_PATH in wp-config.php as that copy's package root (the folder that contains php/):

define( 'BFIELDS_FORCE_PATH', WP_CONTENT_DIR . '/plugins/bfields' );

See Versioning & multiple copies for the full rules.

TypeScript types (optional)

The npm package @bplugins/bfields ships types and authoring helpers only, never the runtime. Use it to type a custom field component. At run time, always use window.bfields. If each host bundled the runtime, a page would load several bundles, React roots and window.bfields objects.

import type { FieldComponentProps } from '@bplugins/bfields';

Quick Start

A complete plugin with one settings page, two tabs and a dependency, and code that reads the saved values.

<?php
/**
 * Plugin Name: My Plugin
 */

require_once __DIR__ . '/lib/bfields/php/bootstrap.php';

add_action( 'bfields_loaded', function () {
	add_action( 'init', 'my_plugin_register_settings', 1 );
} );

function my_plugin_register_settings() {
	$prefix = '_my_plugin_settings_';

	\BFields\Compat\Codestar::createOptions( $prefix, array(
		'menu_title'      => __( 'My Plugin', 'my-plugin' ),
		'menu_slug'       => 'my-plugin',
		'framework_title' => __( 'My Plugin Settings', 'my-plugin' ),
		'show_search'     => true,
	) );

	\BFields\Compat\Codestar::createSection( $prefix, array(
		'title'  => __( 'General', 'my-plugin' ),
		'icon'   => 'fas fa-cog',
		'fields' => array(
			array(
				'id'       => 'enabled',
				'type'     => 'switcher',
				'title'    => __( 'Enable feature', 'my-plugin' ),
				'subtitle' => __( 'Turn the whole feature on or off.', 'my-plugin' ),
				'default'  => true,
			),
			array(
				'id'         => 'mode',
				'type'       => 'button_set',
				'title'      => __( 'Mode', 'my-plugin' ),
				'options'    => array(
					'simple'   => __( 'Simple', 'my-plugin' ),
					'advanced' => __( 'Advanced', 'my-plugin' ),
				),
				'default'    => 'simple',
				'dependency' => array( 'enabled', '==', '1' ),
			),
		),
	) );

	\BFields\Compat\Codestar::createSection( $prefix, array(
		'title'  => __( 'Style', 'my-plugin' ),
		'icon'   => 'fas fa-paint-brush',
		'fields' => array(
			array(
				'id'      => 'accent',
				'type'    => 'color',
				'title'   => __( 'Accent colour', 'my-plugin' ),
				'default' => '#1b5cf0',
			),
			array(
				'id'      => 'width',
				'type'    => 'dimensions',
				'title'   => __( 'Width', 'my-plugin' ),
				'height'  => false,
				'default' => array( 'width' => '100', 'unit' => '%' ),
			),
		),
	) );
}

Activate the plugin and open My Plugin in the admin menu. Because save_defaults is on by default, the option already holds every default before anyone saves.

Reading the values

$enabled = bfields_get_option( '_my_plugin_settings_', 'enabled' );        // '1', '0', true …
$mode    = bfields_get_option( '_my_plugin_settings_', 'mode', 'simple' ); // 'simple'
$width   = bfields_get_option( '_my_plugin_settings_', 'width' );          // array( 'width' => '100', 'unit' => '%' )

if ( $enabled ) {
	printf( '<div style="max-width:%s%s">…</div>', esc_attr( $width['width'] ), esc_attr( $width['unit'] ) );
}

// Or read the whole array, exactly as Codestar stored it.
$options = get_option( '_my_plugin_settings_', array() );
Helpers return the raw stored value without casting. A switcher can be '1', '0', '' (never toggled) or a PHP true/false (seeded or reset). A plain if ( $value ) treats all of them correctly. See Getting values.

How It Works

What happens between createOptions() and a saved row, so you know where to hook in.

  your field arrays (Codestar vocabulary, PHP, request time)
                    │
     \BFields\Compat\Codestar::createOptions / createSection / createMetabox
                    │
               Registry  ──►  Schema::build()  ──►  JSON schema (versioned, "schema": 1)
                                                        │
                        wp_add_inline_script(window.bfieldsBoot[unique])
                                                        │
                                                 React UI (bfields-ui)
                                                        │
   wp_options / postmeta  ◄──  Codec  ◄──  Sanitizer  ◄──  REST / post form  ◄──  store

Request lifecycle

  1. Boot. Every bundled copy calls bfields_register_copy(). On plugins_loaded at priority -1000, the newest copy's loader runs and fires bfields_loaded.
  2. Register. Your calls store the raw arrays. Nothing is normalised yet, because field sets are often decided per request (licence checks, filters, closures).
  3. Seed. On init priority 99, every options screen with save_defaults whose option is empty is seeded with its raw defaults, as Codestar does.
  4. Render. The page prints one mount node, <div class="bfields-root bfields-app">, which contains a server-rendered fallback notice. The bfields-ui bundle is enqueued with that screen's schema and hydrated values. It removes the notice and renders the UI.
  5. Save. Options pages send POST /wp-json/bfields/v1/options/<unique>. Meta boxes copy their values into a hidden field that WordPress submits with the post. Either way PHP shapes each value, sanitizes and validates it, merges the result over the stored row, fires the save hooks and writes.

Authoring type vs. core type

Every field keeps its Codestar type (the authoring type), because the codec and the sanitizer key off it. A second property, core, picks the React component. Several authoring types share one component:

Core componentAuthoring types
toggleswitcher, checkbox without options
choicecheckbox with options, button_set, radio, select, image_select
texttext, textarea, password
numbernumber, spinner, slider
colorcolor
mediamedia, upload
dimensiondimensions
spacingspacing
fieldsetfieldset
repeatergroup, repeater
codecode_editor
linklink
displaycontent, notice, callback, heading, subheading, submessage
unknownAny other type. The value is carried verbatim and shown read-only.

Components are looked up by authoring type first, then by core type. This lets you override one type without replacing the shared component.

What stays in PHP

Everything security-related: menu and meta box registration, capability and nonce checks, sanitization and validation, default seeding, the csf_* hook bridge and version arbitration. The browser validates only for usability. The server never trusts anything the browser sends.

Saving

  • Save Changes sends every declared field to POST /bfields/v1/options/<unique>. Untouched fields are sent exactly as they were loaded. The response is the stored row, which becomes the new baseline. The page does not reload.
  • If a save fails (expired nonce, network error, lost capability), nothing is written, the user's edits stay on screen and a notice shows the reason.
  • If a validate callback rejects a field, that field keeps its stored value and the rest is saved. The notice lists the rejected fields.
  • Reset Section and Reset All ask for confirmation. If other sections have unsaved edits, the confirmation says those edits will be lost.

Deep links

Clicking a tab writes Codestar's hash form, #tab=<slug>, where the slug is sanitize_title() of the section title. Existing links such as admin.php?page=my-plugin#tab=analytics keep working, and #tab=<section-id> works too.

The page body gets the class bfields-screen, so the admin background can match the app. The bundle loads only on screens that bfields registered.

Every row in the design has a 40px icon tile, but Codestar fields have no icons. bfields therefore decides per section: if any field in a section has an icon, every row in that section gets a tile, using a generic mark where none is set. Otherwise no row does. This keeps the titles aligned.

How meta boxes save

A meta box has no REST call. WordPress's own Publish / Update saves it, in WordPress's own request:

  1. The box prints a nonce and a hidden <textarea name="bfields_values[<unique>]">. The textarea is disabled and empty.
  2. On mount, the bundle enables it and keeps the JSON of every declared value in it.
  3. On save_post, bfields verifies the nonce and capabilities, decodes the JSON, then sanitizes, validates and merges it over the stored row.

If the bundle never runs, the disabled field is not submitted and saving the post writes nothing, rather than a stale or empty copy. Autosaves and revisions never write meta.

If a validate callback rejects a value, the message is kept in a short per-user transient and shown in the box after the redirect, once.

Tabs in a meta box

A meta box with more than one section shows its sections as tabs across the top of the box. tabs_position, tabs_switcher, search and the reset buttons belong to options pages. The plain meta box does not use them.

No default seedingMeta boxes are never seeded, as in Codestar. A field the post has no value for shows its default. The first save writes what a Codestar save would have written for it.

How it differs from Codestar

  • The function runs on the server when the schema is built, once per request. Its output is captured and inserted into the page as HTML.
  • The markup is left exactly as the function printed it, so other scripts can target it by id. A live preview's root element is the typical use.
  • <script> tags inside the output do not run, because browsers skip scripts inserted as HTML. Enqueue your script separately and find your element with it. bfields.subscribe() gives it the values.

How rows are saved

  • New rows are built from the sub-fields' defaults, so they arrive complete.
  • Existing rows are patched, never rebuilt. Saving an old record under a newer field set does not add empty keys for sub-fields the row never had. A row gains a key only when the user sets it. Codestar, by contrast, rewrites every row with every declared sub-field.

  • The client-side row id used for reordering is stripped and never reaches the database.
  • Inside a row, a dependency resolves against the row's own values first, then the screen's. 'all' skips the row.
  • As in Codestar, sanitize and validate run on top-level fields only. Row values are shaped by their sub-field's type and passed through wp_kses_post().

Field Features

Dependency

Show a field only when other fields have certain values. bfields uses Codestar's syntax and operators and evaluates them against the form's values, not the DOM.

Syntax

// One rule: controller, operator, value
'dependency' => array( 'loader_type', '==', 'image' ),

// Several rules, all must match (AND)
'dependency' => array( 'enabled|loader_type', '==|!=', '1|none' ),

// The same as a list of rules
'dependency' => array(
	array( 'enabled', '==', '1' ),
	array( 'loader_type', '!=', 'none' ),
),

// 4th element: look the controller up at the top level of the screen
'dependency' => array( 'loader_type', '==', 'image', 'all' ),

Operators

OperatorShows the field when the controller's value…
==equals the value
!=does not equal the value
> >= < <=compares numerically
anyis one of a comma-separated list: array( 'type', 'any', 'image,video' )
not-anyis not in the list
()Codestar's "call a global JS function" operator. It has no meaning here and always shows the field.

An unknown operator hides the field. An empty operator shows it.

How values compare

  • Booleans are coerced as Codestar does. '1', 1, true and 'true' are true. '0', 0, false, 'false' and null are false.
  • == is JavaScript's loose equality, so a switcher that was never toggled ('') matches '0'. array( 'enabled', '==', '0' ) shows its field on an old record, just as Codestar does.
  • A multi-value controller (a checkbox list, a multiple select) is compared as its comma-joined values for ==/!=. any/not-any check each member.

Scope inside groups and fieldsets

Inside a group row or fieldset, a controller id is looked up in the same row first, then at the top level of the screen. Add the 4th element ('all', or any non-empty value) to skip the row and look only at the top level.

array(
	'id'     => 'hotspots',
	'type'   => 'group',
	'fields' => array(
		array( 'id' => 'has_link', 'type' => 'switcher', 'title' => 'Link' ),
		array(
			'id'         => 'url',
			'type'       => 'text',
			'title'      => 'URL',
			'dependency' => array( 'has_link', '==', '1' ),               // this row's switcher
		),
		array(
			'id'         => 'style_note',
			'type'       => 'notice',
			'content'    => 'Styled globally.',
			'dependency' => array( 'hotspot_style', '==', 'custom', 'all' ), // a top-level field
		),
	),
),
One small differenceCodestar applies the 4th-element flag to a field's whole dependency. bfields applies it per rule, so a list of rules can mix row-local and top-level controllers. For every form Codestar accepts, the result is the same.

Hidden is not deleted

A hidden field keeps its value and is still sent on save, as in Codestar. Dependencies only decide what is shown.

Field Features

Sanitize & Validate

bfields applies Codestar's rules exactly, so a Classic save and a bfields save of the same input store the same bytes. Sanitization always runs in PHP. Nothing the browser sends is trusted.

The rules

Field has…What happens on save
no sanitizewp_kses_post(), deep for arrays, for every type, URLs and colours included. & in a URL becomes &amp;. > in CSS becomes &gt;. Non-string scalars (a seeded true, an int) are left as they are.
a callable sanitizeCalled with the value alone, instead of kses. 'sanitize' => 'absint' and 'esc_url_raw' are safe.
'sanitize' => falseSaved as posted, with no filtering at all.
a callable validateCalled with the value. A non-empty return is an error message: the field keeps its stored value and the message is shown. Everything else is saved.

Before any of this, the value is put into the field type's stored shape: an 8-key media array, a string for a single select, and so on.

Example

array(
	'id'       => 'items_per_page',
	'type'     => 'number',
	'title'    => __( 'Items per page', 'my-plugin' ),
	'sanitize' => 'absint',
	'validate' => 'my_plugin_validate_per_page',
),

function my_plugin_validate_per_page( $value ) {
	if ( (int) $value < 1 || (int) $value > 100 ) {
		return __( 'Choose a number between 1 and 100.', 'my-plugin' );
	}
	return ''; // valid
}

Where the message appears

  • Options page: the save response lists the errors, and the notice reads "Saved, except: Items per page: Choose a number between 1 and 100."
  • Meta box: the messages survive the post-save redirect in a five-minute, per-user transient and appear once at the top of the box.

Scope

As in Codestar, sanitize and validate run on top-level fields only. Sub-fields of a group or fieldset are shaped by their own type and passed through kses, and their callbacks are not run. Responsive device keys ({id}_tablet, {id}_mobile) run through the same callbacks as the field.

Filters

After the rules above, every value passes through two filters. Use them to sanitize a custom field type:

add_filter( 'bfields_sanitize_my_rating', function ( $value, $field ) {
	return (string) min( 5, max( 0, (int) $value ) );
}, 10, 2 );

add_filter( 'bfields_sanitize', function ( $value, $field ) {
	return $value; // every field, every type
}, 10, 2 );
Keep sanitizers idempotentA sanitizer must return a stored value unchanged: sanitize( $stored ) === $stored. Otherwise every save rewrites data the user never touched.

Default Values

Write default in the field's stored shape. bfields seeds and resets exactly as Codestar does.

Seeding options pages

With save_defaults on (the default), an options screen whose option is empty is seeded on init priority 99, on every request, frontend included:

  • Every declared field is written with its raw authored default, so 'default' => true is stored as PHP true and 20 as an int. A field without a default gets ''.
  • pro fields, display fields and responsive device keys are not seeded.
  • Only the _saved hook fires, as in Codestar.
  • Seeding is skipped as soon as the option has any value. The check is cheap: the schema is built only when seeding is actually needed.

Reading responsive values

Apply the same inheritance as the UI: tablet falls back to desktop, and mobile falls back to tablet.

/**
 * A responsive scalar field ({id}_tablet / {id}_mobile keys).
 */
function my_responsive_value( array $row, string $id, string $device = 'desktop' ) {
	$empty = static function ( $value ) {
		return null === $value || '' === $value || array() === $value;
	};

	$desktop = isset( $row[ $id ] ) ? $row[ $id ] : '';
	$tablet  = isset( $row[ $id . '_tablet' ] ) && ! $empty( $row[ $id . '_tablet' ] ) ? $row[ $id . '_tablet' ] : $desktop;
	$mobile  = isset( $row[ $id . '_mobile' ] ) && ! $empty( $row[ $id . '_mobile' ] ) ? $row[ $id . '_mobile' ] : $tablet;

	return 'mobile' === $device ? $mobile : ( 'tablet' === $device ? $tablet : $desktop );
}

/**
 * A responsive dimensions / spacing value (tablet and mobile nested inside).
 */
function my_responsive_size( $value, string $device = 'desktop' ): array {
	$value = is_array( $value ) ? $value : array();

	// A device set counts once any key other than its unit has a value.
	$set = static function ( $candidate ) {
		if ( ! is_array( $candidate ) ) {
			return false;
		}
		foreach ( $candidate as $key => $item ) {
			if ( 'unit' !== $key && is_scalar( $item ) && '' !== (string) $item ) {
				return true;
			}
		}
		return false;
	};

	$desktop = array_diff_key( $value, array( 'tablet' => 0, 'mobile' => 0 ) );
	$tablet  = $set( $value['tablet'] ?? null ) ? $value['tablet'] : $desktop;
	$mobile  = $set( $value['mobile'] ?? null ) ? $value['mobile'] : $tablet;

	return 'mobile' === $device ? $mobile : ( 'tablet' === $device ? $tablet : $desktop );
}

$options = get_option( '_my_settings_', array() );
$size    = my_responsive_value( $options, 'font_size', 'mobile' );
$width   = my_responsive_size( $options['viewer_width'] ?? array(), 'tablet' ); // array( 'width' => '80', 'unit' => '%' )

Add a type bfields does not ship, port a custom CSF_Field_* class, or replace the control for one built-in type.

1. Map the type in PHP

Tell bfields which core type your field is closest to. Without a mapping it is unknown and shown read-only.

add_filter( 'bfields_type_map', function ( $map ) {

Saving

Always save through BFields\Storage\PostMeta. It sanitizes and validates against the schema, merges over the stored row, applies wp_slash() for update_post_meta(), and fires the save hooks with the post id.

add_action( 'save_post_my_viewer', function ( $post_id ) {
	if ( wp_is_post_revision( $post_id ) || ( defined( 'DOING_AUTOSAVE' ) && DOING_AUTOSAVE ) ) {
		return;
	}
	if ( ! isset( $_POST['my_viewer_nonce'] ) || ! wp_verify_nonce( sanitize_text_field( wp_unslash( $_POST['my_viewer_nonce'] ) ), 'my_viewer_' . $post_id ) ) {
		return;
	}
	if ( ! current_user_can( 'edit_post', $post_id ) || empty( $_POST['my_viewer_values'] ) ) {
		return; // absent payload: write nothing
	}

	$values = json_decode( wp_unslash( $_POST['my_viewer_values'] ), true );
	$schema = \BFields\Registry::instance()->schema( '_my_viewer_' );

	if ( is_array( $values ) && array() !== $values && $schema ) {
		$storage = new \BFields\Storage\PostMeta( $post_id, '_my_viewer_' );
		$storage->save( $values, $schema );
		$errors = $storage->errors(); // field id => validate() message
	}
} );

Versioning & Multiple Copies

Several plugins on one site can each bundle bfields. Only the newest copy loads, so a page has one runtime, one bfields-ui script and one window.bfields.

How arbitration works

  1. Each copy's php/bootstrap.php records its version and path with bfields_register_copy(). It defines no classes.
  2. On plugins_loaded priority -1000, bfields_boot_newest() sorts the copies with version_compare() and loads the highest.
  3. The winner defines its constants, registers its autoloader and fires bfields_loaded.

At equal versions, the copy registered last wins. $GLOBALS['bfields_loaded_from'] names the loader that won, and $GLOBALS['bfields_copies'] lists every copy recorded.

Constants

ConstantValue
BFIELDS_VERSIONThe winning copy's version. Only the winner defines it.
BFIELDS_PATHThe winning copy's package root, with a trailing slash.
BFIELDS_URLIts URL. This works from any plugin folder, mu-plugins included.
BFIELDS_SCHEMAThe JSON schema version, 1.
BFIELDS_FORCE_PATHYours to define in wp-config.php. It makes the copy at that package root win outright. Development only.

Compatibility promises

  • No breaking changes under this package name. A newer copy serves older hosts, so a breaking release would break them. A breaking change ships as bfields2 / BFields2\ and coexists.
  • The codec is frozen at v1. Stored shapes never change. Changes are additions only.
  • The schema format is versioned. A bundle and a server that disagree refuse to render or save, rather than guess.
  • The global CSF class is never defined. Codestar checks class_exists( 'CSF' ), so a polyfill would take over every other Codestar-based plugin on the site.

Fallback & Troubleshooting

A screen whose script fails is never blank, and saving it never loses data.

The fallback notice

Every mount node contains server-rendered markup, which the bundle removes when it mounts. The bundle mounts once every script on the page has run (DOMContentLoaded), so on a heavy admin page or a slow host that can take a while. Until then the node says "Loading these settings…" (meta box) or "Loading the settings…" (options page), with a spinner.

If the bundle is blocked, returns 404 behind a cache or optimisation plugin, or throws first, the loading line turns into a notice:

  • Options page: "This screen is taking longer than usual to load, or it could not load on this site. Your saved settings are safe and unchanged."
  • Meta box: "These settings are taking longer than usual to load, or they could not load on this site. Nothing has changed: saving the post will not change them."

When the notice appears:

  • At once, if the bundle ran and gave up (no payload, a schema mismatch), or JavaScript is off.
  • bfields_fallback_delay seconds (default 5) after DOMContentLoaded, if the bundle has not run by then. The delay leaves room for a bundle an optimisation plugin loads late.
  • 60 seconds after the page first drew it, by CSS alone, when the small inline script that does the above cannot run (a strict Content Security Policy, or an earlier script on the page that never finishes loading).

Give it a "Switch to the classic interface" button with bfields_fallback_url. A render error after mount is caught by an error boundary that shows the same way out.

Migrating from Codestar

Your field arrays and stored data stay as they are. You change the class your registration calls go to.

Steps

  1. Bundle bfields at lib/bfields/ and require its bootstrap. See Installation.
  2. Register on bfields_loaded, then init, before priority 99.
  3. Swap the class: \CSF:: becomes \BFields\Compat\Codestar::. The arguments are the same.
  4. Keep your csf_* hooks. They still fire, with the same arguments and in the same order.
  5. Check the differences below, especially headings, select placeholders and unsupported types.
  6. Optionally add bfields keys such as icon, layout, pro and responsive. Codestar ignores them.

Supporting both renderers

During a transition, route every registration through one small class. The same arrays then feed Codestar (Classic) or bfields (Modern), and neither UI can declare a field the other lacks:

final class My_Registrar {

		self::modern() ? \BFields\Compat\Codestar::createOptions( $unique, $args ) : \CSF::createOptions( $unique, $args );
	}

	public static function metabox( string $unique, array $args ): void {
		self::modern() ? \BFields\Compat\Codestar::createMetabox( $unique, $args ) : \CSF::createMetabox( $unique, $args );
	}

	public static function section( string $unique, array $section ): void {
		self::modern() ? \BFields\Compat\Codestar::createSection( $unique, $section ) : \CSF::createSection( $unique, $section );
	}

	private static function modern(): bool {
		return class_exists( '\BFields\Compat\Codestar' ) && 'classic' !== get_option( 'my_plugin_admin_ui', 'modern' );

FAQ

Does bfields ever migrate or rewrite my data?

No. It reads and writes Codestar's exact format, and a value changes only when a user changes it. There is no migration step, and there never will be one.

Can Codestar and bfields run on the same site?

Yes. bfields never defines the global CSF class, so other Codestar-based plugins are unaffected. One plugin can even offer both renderers for the same screen. See Migrating.

Is the UI available on the frontend?

No. bfields renders admin screens only. Seeding runs on every request, so frontend code can read seeded values.

Can I use bfields without Codestar arrays?

The Codestar facade is the authoring API today. \BFields\Registry::instance()->options(), metabox() and section() are the underlying calls, but they do not bridge the csf_* hooks.

Why does saving send every field, not only the changed ones?

The server merges what it receives over the stored row. With a partial payload, a field whose seeded or legacy value was never sent could silently revert. Untouched values are sent exactly as they were loaded, so they are written back as the same bytes.

Where do labels get translated?

In PHP, with your own text domain. Labels travel inside the schema. Only the framework's own strings (Save Changes, Reset All…) use the bfields text domain.

Which React version does it use?

WordPress's own, from wp.element. bfields never bundles React, so its UI and your scripts share one React.
